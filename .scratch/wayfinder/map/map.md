## Destination

A buildable, phased implementation plan (engineering spec) for the tie-payments **core platform**: the 5-pillar payment orchestration + invoicing + subscriptions + webhooks + dynamic schema engine, plus sandbox/mock-gateway and Hosted Payment Pages — **API-only** (no merchant Admin UI), delivered as a **modular monolith** on **Bun + ElysiaJS + SurrealDB**, with minimal, justified dependencies. Plan is "clear" when every decision below is resolved and nothing is left to decide before implementation starts.

## Notes

- **Domain**: Payment orchestration / TSP. GCC + Bahrain regulatory posture (CBB PS-1.1.3, PCI SAQ A via client-side tokenization, PDPL, VAT 5%). See `SPEC.md`.
- **Stack fixed**: Bun runtime (latest, `1.3.x`), ElysiaJS framework, SurrealDB. Minimal deps is a hard constraint — **every** dependency choice must be justified in the ticket's resolution (what it buys, what breaks without it, what it costs).
- **Elysia 2.0** (daydream, full rewrite, still beta): target `elysia@next` for the plan; AOT build-mode compilation, `@elysia/` scoped plugins, new error API (Problem Details RFC 9457), `derive` replaces `resolve`, lifecycle renames (`onError→error`). See blog `elysiajs.com/blog/elysia-20.html`; migrate legacy examples with `bunx @elysia/codemod`. Backend agent + `elysiajs` skill must follow 2.0 syntax.
- **Skills to consult**: `elysiajs` for backend patterns; `find-docs`/`ctx7` for library facts; `grilling` + `domain-modeling` for design tickets.
- **Tooling (project setup)**: specialized subagents in `.opencode/agent/` — `db-ops` (SurrealDB), `backend` (ElysiaJS/Bun), `payments-gcc` (GCC/payments domain). Skills installed globally in `~/.agents/skills/` (surrealdb/agent-skills set, elysiajs, stripe-best-practices). MCP: `surrealdb` (built-in stdio MCP, needs `surreal` binary v3.1+ on PATH) and `stripe` (remote mcp.stripe.com). See `AGENTS.md`. Sessions must delegate to the matching subagent and use the matching skill.
- **Scope**: core platform only. SDKs, ecosystem plugins, merchant Admin UI are **out of scope**.
- **Delivery**: phased milestones (sandbox+mock → invoicing → subs → webhooks → schema/theme).
- **Tracker**: GitHub issues in `AhmedAlSaeed/tie-payments` (this repo). Map = issue #1 (label `wayfinder:map`); tickets = sub-issues; blocking = native GitHub issue deps. Local mirrors under `.scratch/wayfinder/`. See `docs/agents/issue-tracker.md` "Wayfinding operations".

## Decisions so far

<!-- one line per closed ticket: enough to judge relevance, then zoom the link for the detail -->

- [SurrealDB modeling for the payments domain](.scratch/wayfinder/tickets/01-surrealdb-modeling.md) — SCHEMAFULL + DEFINE FIELD for entities, `object FLEXIBLE` for payload bags; custom fields via indexed metadata paths; per-table `merchant`+`environment` composite indexes + `PERMISSIONS WHERE merchant`; money = `decimal`; explicit `BEGIN/COMMIT TRANSACTION` for money moves; state machines enforced in the Bun domain layer; idempotency = composite UNIQUE key + outbox rows written in-transaction; `:ulid()` record IDs.
- [Gateway landscape: which drivers for v1](.scratch/wayfinder/tickets/02-gateway-landscape.md) — v1 driver set: Mock (sandbox default), **Tap** (primary, Bahrain), **Stripe** (global), **Moyasar** (KSA); stretch Checkout.com. Jaywan + direct BENEFIT are NOT drivers (UAE scheme / ISO 20022 rail). Abstraction seams: createPayment→action, tokenize (client-side), auth/capture/refund/void, webhook→event. Currency exponent carried (BHD=3 decimals). Mock matrix mapped to real cards.
- [API surface & modular monolith](.scratch/wayfinder/tickets/04-api-surface.md) — monolith: `core/` shared kernel + `modules/<pillar>/` plugins, in-process comms via service imports, persistence behind store interfaces. API: `sk|pk_<test|live>_<40hex>` keys; env always derived from prefix; `Bearer` auth; `Idempotency-Key` namespaced (replay vs 409 conflict); RFC 9457 `{type,title,status,detail,code,instance}`; `/v1` versioning (major = second router mount). **Elysia 2.0-beta**: route signature `get/post(path, hook, fn)` (NOT 1.x path,fn,hook); `.error(Class, fn)` + `instanceof` discrimination (no `code` on context); a `headers` schema replaces `context.headers` so read `authorization` via `request.headers`. Deps: `elysia@next` + `typebox` only.
- [Unified gateway abstraction contract](.scratch/wayfinder/tickets/03-gateway-abstraction.md) — T03 kernel in `src/core/gateway/`. Port `GatewayDriver` (createPayment required; tokenize/capture/refund/void/normalizeWebhook optional) + `capabilities`. Closed normalized `GatewayErrorCode` set on `GatewayError` with a `retryable` flag (single failover/dunning signal). Money = minor units + currency (exponent from `CURRENCY_EXPONENT`, BHD=3). `ChargeAction` = redirect|qr|client_secret|hosted_page|none. Routing: ordered `RoutingRule {id, if{}, driver, failover?}`, dependency-free `matchRule`, sandbox→mock default. Cross-gateway token = unified `tok_…` holding `driverId→gatewayToken` map. Mock driver implements SPEC 4.3 (4242/0002/9999/3D01/QR), 30ms latency. `PaymentService` takes the driver per method; plugin `routeDriver` throws `gateway_error` (502) if unconfigured.
- [Invoice engine state machine & VAT](.scratch/wayfinder/tickets/05-invoice-engine.md) — **adopts Stripe's Invoicing model**. Stored statuses `draft | open | paid | voided | uncollectible`; `overdue` = derived (open ∧ due past ∧ remaining>0); `partial` = derived (open ∧ paid>0). No currency conversion in-engine (single `currency` per invoice; payments in that currency). Overpay → customer credit balance. `collection_method`: `send_invoice` (HPP/payment-link, `hosted_invoice_url`) vs `charge_automatically`. Amounts: `amount_subtotal/discount/tax/shipment/due/paid/remaining/overpaid`. Tax = explicit rate objects (seed **BH 5% VAT**, incl/excl per rate, TIN on merchant); `automatic_tax` lookup out of scope. Discounts line-then-invoice-level, `discountable` gate. Money = minor-units `int` (codebase `Money`, supersedes T01 decimal for invoice). Events feed T06/T07. SurrealDB schema block in ticket.
- [Subscription engine & dunning](.scratch/wayfinder/tickets/06-subscription-engine.md) — **adopts Stripe's Subscriptions model**. Statuses `trialing | active | past_due | incomplete | canceled`; recurrence = `interval`+`interval_count` (no cron strings; `billing_cycle_anchor` defaults to `created_at`); pricing via `billing_scheme` (per_unit/metered/tiered) covering flat/seat/usage/tiered in one mechanism. Durable = Stripe automation: retry schedule + max-attempt budget, driver `retryable`-classified (T03), auto-cancel on exhaustion, durable outbox. Trial defers first charge to cycle-end. Proration via `credit_balance` (reuses T05). Cancellation modes: `cancel_at_period_end` / `cancel_at` / immediate. Period-close automation creates+finalizes the cycle invoice (T05) honoring `collection_method`. Schema: `price`, `subscription`, `subscription_item`, `usage_record`, `dunning_attempt`.
- [Event bus & webhook engine](.scratch/wayfinder/tickets/07-webhook-engine.md) — **canonical-only feed**: gateway webhooks are de-duplicated + drive state, which re-emits canonical events (`payment.*`, `invoice.*`, `subscription.*`, `ping`) via a durable SurrealDB **outbox** written in-transaction (T01 pattern) + in-proc EventBus — no broker. Stripe v1 envelope `{id,type,data:{object_type,object_id,object}}` (full snapshot). Delivery = in-proc Svix model: `webhook_endpoint` with HMAC-SHA256 `tie-timestamp`/`tie-signature`, per-attempt `event_delivery`, at-least-once deduped by `event_id`, ordering per `object_id`. Retry = exp backoff (10s, ×2, cap ~1.8h), default `max_attempts` **3**, dead-letter on exhaustion. Inbound gateway dedup = UNIQUE (merchant, env, driver_id, gatewayEventId) → replay 200 no-op. Replay = re-send stored envelope (`POST .../events/{id}/redeliver`); query APIs (`GET /v1/events`, `/v1/event_deliveries`) ship now for the future admin streamer. Schema: `outbox_event`, `event_delivery`, `webhook_endpoint`.
- [Sandbox, mock gateway & testing env](.scratch/wayfinder/tickets/08-sandbox.md) — **onboarding gates on Better Auth**: signup auto-provisions `merchant` + `sk_test`/`pk_test` (hash-stored) + default mock `RoutingRule`, returns 1-line SDK snippet. Zero-leak isolation enforced by DB row-level `PERMISSIONS` scoping (env always from key prefix, never body). Simulated payments drive the **real** inbound `webhook→canonical` pipeline (T07) so merchants observe genuine events. `3D01` → guarded `/mock/3ds` challenge page that posts completion through the same inbound path. Streamer = **API-only** (`GET /v1/event_deliveries`; UI out of scope). `context.ts` binding switches from hash-stub to `api_key→merchant` record. Schema adds `api_key` (+`merchant`, `routing_rule` reuse); mock stays stateless.
- [Dynamic schema engine & SDK auto-render](.scratch/wayfinder/tickets/09-schema-engine.md) — **JSON Schema 2020-12 is the custom-field contract** (no new DSL): `field_schema` per `(merchant, environment, target_entity)`; values stored in each aggregate's `metadata` `object FLEXIBLE` with per-path indexes (T01 pattern, no EAV). Value validation in the **Bun service layer** at write (fail-fast), DB typing as backstop. SDK-ready render contract = raw schema + per-field `ui:` extensions (label/placeholder/helper/choices/disabled/locale) served `GET /v1/schema/{target_entity}` — matches SPEC §3.2 exactly. Admin CRUD = PUT/GET/DELETE with `version`+`updated_at` optimistic concurrency (`If-Match`), Idempotency-Key + RFC-9457. Deletion keeps stored values, stops validating. Plus lightweight `theme` table (colors/radius/dark/CSS/branding/locale) feeding the deferred HPP. Schema: `field_schema`, `theme`.
- **Deployment & multi-tenant tenancy** — **adopts SurrealDB-native isolation**: **one `DEFINE DATABASE` per tenant** (optionally a `namespace` per tenant group), **not** a master+node-per-tenant fleet (not SurrealDB's model — multi-node = N query nodes on shared storage, SurrealDS/Cloud `Scale`). Data residency (Saudi→Saudi, Bahrain→Bahrain) = choose **regional SurrealDB instances**; a **config-driven `tenant_registry`** (tenant → region/instance) is the only new piece, consulted by `context.ts`/API-key resolution (replaces the pooled-single-DB assumption where hard isolation is wanted). Scaling = horizontal query nodes, never per-tenant servers. Pay-as-you-go + credit subs ride the **existing** engine: T05 credit-balance + T06 metered plans, keyed per tenant — no new billing machinery. Hardly any rework: schemas/PERMISSIONS stay; the registry just picks the tenant's DB.
- **Rate limiting** — **token-bucket, per API key** (keyed on `api_key.hash` + route), burstable; generous merchant default (e.g. 100 rps / 10k burst). On exceed: `429` + `Retry-After` + RFC-9457 `rate_limited`. **In-memory only for v1** (monolith single-process) — no shared/Redis store unless multi-instance deployment later.
- **API-key rotation & lifecycle** — `POST /v1/api_keys/{id}/rotate` mints a new key; old key enters a **dual-active grace window (default 7 days)** where both are valid, then is revoked (`active=false` + `rotated_at`). `GET /v1/api_keys` lists masked prefixes; a raw secret is **returned once at creation and never re-served**. Manual revoke endpoint stops a key immediately.
- **Smart-routing rule model** — **ordered static rules + driver `failover` chain** (`RoutingRule { id, position, if {currency?, method?, card_brand?, amount_gte?, amount_lte?, environment?}, driver, failover?: string[] }`); unmatched → merchant **default driver** (sandbox → mock). **Dynamic lowest-fee ranking OUT of v1** (needs live fee/health state we don't hold); noted as a stretch expressed later as a special `if`/rank action, no new machinery needed.

## Not yet specified

- **Security detail**: PCI SAQ-A attestation process, PDPL data-processing agreement. **Key namespacing (T04/T08) and rotation/lifecycle policy now settled** under Decisions-so-far; PCI/PDPL attestation process remains.
- **HPP & theme contract**: how merchant branding/theme config surfaces through the API into hosted pages; localization/RTL contract. Depends on customization-engine decision (T09 `theme` table is the seam).
- **Rate limiting**: token-bucket vs sliding window, key scope, 429 semantics. Follows on from the API-surface decisions.

## Out of scope

- **Merchant Admin Portal UI** — API-only was decided; admin features (webhook replay, schema editor, theme config) are API resources.
- **Official SDKs** (Node/TS, Python) and **ecosystem plugins** (Odoo/Magento/WooCommerce) — a later effort.
- **Global-gateway deep integrations beyond the v1 driver set** — deferred behind the gateway ticket.
- **PCI certification process** — compliance posture is designed in, certification itself is out.
